# 01 - Git 版本控制规范

> - 🟢 本文件适用于所有使用 Git 的单人开发与多人协作项目（业务工程、工具库、客户端、服务端与内容资产仓库）。
> - 🔴 不适用：强行覆盖目标仓库已有的分支模型（如 GitFlow / Trunk-Based）、托管平台权限策略或 CI 门禁配置。

---

## 1. 分支模型与创建时机

🟡 **推荐默认模型**：以 **主干短分支模式（GitHub Flow 变体）** 为默认基准——以主分支（`main`）为稳定主干，需求、修复与实验改动在短生命周期工作分支完成，验证通过后合入主干并删除分支。若团队需要并行维护预发布回归线，可按需从主干拉出 `release/vX.Y.Z`；若目标仓库已稳定运行 GitFlow（含 `develop`）或 Trunk-Based，沿用仓库既有约定，不得擅自迁移。

### 1.1 各类分支的创建时机、来源与生命周期

| 分支类型 | 什么时候建 | 从哪拉出 | 合并目标 | 生命周期与清理 |
|---|---|---|---|---|
| `main`（或仓库既定 `master`） | 仓库初始化时建立 | — | — | **永久保留**；始终保持可构建、可测试、可发布 |
| `feat/<slug>`（或仓库既定 `feature/<slug>`） | 承接独立功能、页面或模块开发前 | 最新的 `main`（GitFlow 下为 `develop`） | `main`（或 `develop`） | **短生命周期（建议 1–5 天）**；合入后立即删除远端与本地分支 |
| `fix/<slug>` | 修复开发/测试阶段发现的缺陷时 | 最新的 `main`（封板期 Bug 可从 `release/*` 拉出） | 来源分支 | 修复验证合入后立即删除 |
| `hotfix/<slug>` | 线上已发布版本爆发紧急故障、且主干已含未发布新功能时 | **线上对应正式发布 Tag**（如 `v1.2.0`） | 发布新 Patch Tag 并**回并** `main` / `develop` | 发布并回并主干后删除 |
| `release/vX.Y.Z` | 迭代进入封板（Code Freeze）且需与下个迭代开发并行时 | 达到封板状态的 `main` / `develop` | 打 `vX.Y.Z` Tag 并回并主干 | 仅接受 Bugfix 与发版元数据更新；发版回并后删除 |
| `refactor/<slug>` / `docs/<slug>` / `chore/<slug>` / `test/<slug>` | 独立重构、纯文档调整、依赖/构建变更或测试补充时 | 最新的 `main` | `main` | 完成后合入并删除 |

### 1.2 单人开发与多人协作的建分支原则

- 🔴 **多人协作场景**：凡涉及代码、配置、依赖、规则或资产变更，开始修改前必须先同步目标基线再切出独立工作分支，经评审（PR / MR）与校验后合入；**禁止在未同步的陈旧本地分支或受保护主分支上直接堆砌未评审改动**。
- 🟡 **单人开发场景**：低风险小改动（如单处文档修正、微小配置调整）在仓库未开启分支保护时可按需直接提交主干；但凡涉及**跨多天的新功能、较大重构、依赖升级或不确定能否一次跑通的实验性改动**，仍应切出独立工作分支，保证主干随时可回到干净可运行状态，也便于随时切换任务或丢弃失败尝试。
- 🔴 **禁止一分支多需求**：无论单人还是多人，不要把互不相关的多个需求或“顺手重构”混入同一分支，以免难以审查、无法独立回滚或阻塞发布。
- 🟡 **控制分支存活时长**：大需求优先拆分为可独立合入的小步改动（配合特性开关隔离未完工入口），工作分支超过 3 个工作日未同步主干时应主动同步，降低合并冲突成本。

```bash
# ❌ 反例：直接在本地过期的 main 上做大功能，或从别人未合入的开发分支再嵌套切分支
git checkout main
# ...直接修改半成品功能并尝试直接推送到受保护 main...

# ✅ 正例：先拉取最新远端基线，再以清晰命名的短分支开始工作
git fetch origin
git switch main
git pull --ff-only origin main
git switch -c feat/user-session-refresh
```

## 2. 分支命名规范

### 2.1 命名格式与约束

```text
<type>/<short-slug>
<type>/<ticket-id>-<short-slug>   # 关联需求单/缺陷单时使用
```

- 🔴 **仅使用小写英文、数字与连字符（kebab-case），禁止使用中文**：分支名及推送到远端的分支名仅允许小写英文字母 `a-z`、数字 `0-9`、连字符 `-` 与单个路径分隔符 `/`；**禁止中文、空格、大写驼峰和下划线混用**（避免跨操作系统编码差异、URL 转义乱码，以及 Docker Tag、CI 脚本与预览域名拼接失败）。
- 🔴 **必须带明确类型前缀**：从 `feat`、`fix`、`hotfix`、`release`、`refactor`、`docs`、`chore`、`test` 中选择；禁止仅以个人姓名、日期或无意义词命名分支。
- 🔴 **同一仓库内前缀必须一致**：若仓库历史上已经统一使用 `feature/` 或 `bugfix/`，继续沿用该仓库既有前缀，**不得在同一仓库中混用 `feat/` 与 `feature/`**；新建仓库默认推荐简短前缀 `feat/`、`fix/`（与 Commit `type` 保持一致）。
- 🟡 **语义清晰且精炼**：描述段建议 2–5 个英文单词、总长度控制在 50 字符以内，避免只写 `update` 或 `bug`。

### 2.2 分支命名正反例对照

| ❌ 反例 | 问题说明 | ✅ 正例 |
|---|---|---|
| `zhangsan-dev` / `li4` | 使用个人姓名，看不出任务类型与改动内容 | `feat/mcp-secret-masking` |
| `test` / `my-branch` / `tmp` | 无类型前缀、无业务语义，容易遗留成僵尸分支 | `test/source-manager-e2e` |
| `feat/修复登录超时` | 包含中文，易触发跨平台编码、Docker Tag 与 CI 脚本异常 | `fix/login-token-timeout` |
| `feature/addUserLogin` | 使用驼峰且未与仓库前缀风格对齐 | `feat/add-user-login`（或既定 `feature/add-user-login`） |
| `fix_123` / `bugfix/order` | 混用下划线或缺少具体问题说明 | `fix/proj-123-order-rounding` |
| `hotfix/urgent` | 缺少修复版本与故障定位信息 | `hotfix/v1.2.1-crash-on-startup` |
| `release/next` | 未指明目标语义化版本号 | `release/v1.3.0` |

## 3. Git Commit 提交信息规范

🟡 **仓库约定优先**：若目标仓库已强制约定自定义格式（如要求带单号前缀 `[PROJ-123]`），优先遵循仓库既有规范；无特殊约定时，统一采用 **Conventional Commits** 规范，使提交历史可读、可检索，并支持自动生成变更日志。

### 3.1 提交信息标准结构与语言约定

```text
<type>(<scope>): <subject>

<body>

<footer>
```

| 组成部分 | 是否必填 | 编写规则 | 示例 |
|---|---|---|---|
| `type` | ✅ 必填 | 固定英文小写提交类型（见 § 3.2），不得自造类型 | `feat`、`fix`、`refactor` |
| `scope` | 🟡 推荐 | 受影响的模块、包名或功能域（英文小写短词，多个用 `/` 或 `,`） | `(auth)`、`(desktop)`、`(cli)` |
| `subject` | ✅ 必填 | 一句话概括“做了什么”：动词开头、建议 ≤ 50 字符、**末尾不加句号** | `新增私有 Git 源连接测试接口` |
| `body` | 🟢 可选 | 复杂改动必须补充：说明“**为什么这样改**”、关键取舍与影响范围，不流水账复述代码 | `原逻辑未展开 macOS /tmp 符号链接，导致安全校验误判` |
| `footer` | 🟢 可选 | 关联需求/缺陷单（`Closes #42`）或声明破坏性变更（`BREAKING CHANGE: ...`） | `BREAKING CHANGE: 移除旧版 v1 配置文件读取` |

- 🟡 **中英文使用约定**：`type` 与 `scope` 保持英文小写以便自动化工具解析；`<subject>`、`<body>` 以及 PR/MR 标题、Tag 附注说明**允许并推荐中文团队直接使用中文**（“英文前缀 + 中文描述”），减少语义歧义，同一仓库内保持语言风格一致即可。
- 存在破坏性变更时，也可在冒号前加感叹号提示：`feat(api)!: 统一分页返回结构为 items 与 total`，并在 `footer` 写明迁移方式。

### 3.2 提交类型（type）速查表

| `type` | 适用场景 | 对语义化版本的常规影响 | 示例 |
|---|---|---|---|
| `feat` | 新增面向用户或调用方的功能、能力或接口 | 升 `MINOR` | `feat(rules): 新增多线程任务队列规则` |
| `fix` | 修复功能缺陷、边界异常、崩溃或安全漏洞 | 升 `PATCH` | `fix(desktop): 修复 macOS Dock 图标边距偏大` |
| `refactor` | 代码结构重构，**不改变外部可观测行为** | 不升版 | `refactor(core): 抽取来源索引解析公共函数` |
| `perf` | 性能优化（内存、帧率、查询延迟、包体体积） | 按需升 `PATCH` | `perf(render): 合并静态 UI 批次减少 DrawCall` |
| `docs` | 仅文档、注释、README、规范正文变更 | 不升版 | `docs(readme): 补充桌面端启动与验证命令` |
| `test` | 新增、完善或修复单元测试/集成测试 | 不升版 | `test(mcp): 补充脱敏预览与原子写入用例` |
| `style` | 纯排版格式调整（缩进、换行、分号），不改语义 | 不升版 | `style(ui): 统一侧边栏样式变量缩进` |
| `build` | 构建脚本、打包配置、第三方依赖版本变更 | 按需升 `PATCH` | `build(desktop): 更新 Electron 打包资源清单` |
| `ci` | CI/CD 流水线、自动化检查脚本变更 | 不升版 | `ci(github): 新增规则清单漂移校验步骤` |
| `chore` | 非业务源码的仓库维护（`.gitignore`、工具配置） | 不升版 | `chore(repo): 忽略本地构建产物目录` |
| `revert` | 回退先前的错误提交（正文写明被回退 Commit SHA） | 视原改动而定 | `revert: 回退 feat(auth): 启用新版令牌缓存` |

### 3.3 原子提交与提交信息正反例

- 🔴 **原子提交原则**：一个 commit 只表达一个清晰意图。禁止把全仓库格式化、依赖升级与核心业务修复揉进同一个提交；需要同时处理时应拆分为独立 commit。
- 🔴 **禁止提交无法构建的半成品到主干或共享分支**：本地开发中的临时断点如确需暂存，可在个人私有分支临时标为 `wip: ...`，但在合入主干或提 PR 前必须整理（`squash` 或重写）为清晰规范的提交记录。

```bash
# ❌ 反例：信息含糊、缺少类型、或把多个无关改动混在一个提交里
git commit -m "fix"
git commit -m "update code"
git commit -m "修改bug"
git commit -m "完成"
git commit -m "feat: 加了登录顺便修了打包脚本还格式化了全部文件."

# ✅ 正例：英文类型前缀 + 清晰中文描述，颗粒度单一且可独立追踪
git commit -m "fix(auth): 修复刷新令牌并发失效导致重复跳转"
git commit -m "feat(cli): 支持 init --rulepacks 指定多岗位规则组合"
git commit -m "docs(common): 新增 Git 版本控制与软件版本迭代规范"
```

## 4. 推送（Push）、同步与合并底线

### 4.1 推送分支命名与推送前自检

- 🔴 **远端分支名与本地一致**：首次推送工作分支使用 `git push -u origin <branch-name>` 建立上游跟踪，严禁将本地开发分支直接映射推送到受保护主干（如 `git push origin feat/login:main`）。
- 🔴 **推送前必做三项自检**：
  1. 检查 `git status` 与 `git diff --cached`，确认没有误加调试日志、临时缓存、构建产物或密钥文件。
  2. 运行与本次改动相称的构建、静态类型检查、Lint 或测试命令，确认无新增失败；不得随意使用 `--no-verify` 绕过仓库已配置的 Git Hooks。
  3. 核对提交历史（`git log --oneline -n 5`），确认提交粒度与标题符合规范。

### 4.2 同步主干与冲突处理

- 🔴 **合入前先在本地同步并解决冲突**：发起 PR 或准备合并回主干前，若目标主干已有新提交，必须先在本地拉取最新主干解决冲突并重跑验证，不得把存在合并冲突或未经验证的分支直接交给评审人。
- 🟡 **按分支是否多人共享选择同步方式**：
  - **单人使用的私有分支**：可用 `git fetch origin && git rebase origin/main` 保持提交历史线性整洁。
  - **多人共同开发的共享分支**：统一使用 `git fetch origin && git merge origin/main` 合并最新主干，**严禁在多人共享分支上执行 rebase 改写公共历史**。

### 4.3 PR / MR 评审与合并策略

- 🟡 **PR / MR 标题与描述**：标题采用与 Commit 一致的 `<type>(<scope>): <subject>` 格式（推荐英文前缀 + 中文描述）；描述中写明背景目标、核心变更、验证命令及结果、影响范围（UI 改动附截图，数据/配置改动说明兼容性）。单人仓库若不走 PR，也应在合入提交或里程碑说明中保持同等清晰度。
- 🟡 **按仓库约定统一合并策略**：
  - **Squash and Merge（默认推荐用于日常特性/修复分支）**：将分支内的多次过程提交压缩为一条干净提交合入主干，保持主干日志可读且易于按需求回滚。
  - **Merge Commit**：适用于 `release/*`、`hotfix/*` 回并主干，或仓库需完整保留分支拓扑的场景。
  - **Rebase and Merge**：仅在分支内每条提交都已整理为独立原子提交时使用。
- 🔴 **合入后及时删分支**：分支合入主干后立即删除远端已合并分支，并在本地同步清理（`git branch -d <branch>` 与 `git fetch --prune`），防止陈旧分支被误复用。

### 4.4 禁止的高危操作与安全底线

- 🔴 **严禁对共享或受保护分支执行强推**：绝对禁止对 `main`、`master`、`develop`、`release/*` 等主干或共享分支使用 `git push --force` / `git push -f`；仅在个人私有特性分支确因 rebase 需要更新远端时，使用带远端变更保护的 `git push --force-with-lease`。
- 🔴 **已推送主干/共享分支的回退只能用 `revert`**：已合入主干或共享分支的错误提交必须使用 `git revert <commit>` 生成新的逆向提交，严禁抹除公共历史。
- 🔴 **破坏性本地重置必须先获授权**：`git reset --hard`、`git clean -fd`、`git checkout -- .` 等会永久丢弃未提交改动的破坏性操作，必须先向用户说明数据丢失风险并获得明确授权后方可执行。
- 🔴 **严禁凭据与未受管大文件入库**：`.env`、私钥、访问令牌、证书、本地构建缓存必须纳入 `.gitignore`；大体积二进制资产按仓库约定接入 Git LFS（各技术栈细则见对应语言包的版本控制规则）。一旦密钥误推远端，**第一步必须立即吊销并轮换密钥**，再由管理员评估是否清理历史。

## 5. 提交与协作完成前自检

发起提交、推送或合入前逐项核对：

- [ ] 新功能、重构或多人协作任务是否从最新的目标基线拉出独立短分支，未污染主干
- [ ] 分支名是否符合 `<type>/<short-slug>`（全小写英文与连字符、前缀与仓库一致、不含中文或人名）
- [ ] 提交粒度是否原子化，Commit 标题是否符合 `<type>(<scope>): <subject>`（英文前缀，中文描述清晰）
- [ ] 是否已检查 `git status` / `git diff`，无密钥、调试残留、构建缓存或无关改动
- [ ] 是否已同步最新目标主干、解决冲突并运行对应的构建/检查/测试命令
- [ ] 推送是否指向同名远端分支，未对主干或共享分支使用 `--force` 或绕过门禁
- [ ] 分支合入主干后是否已及时删除不再使用的远端与本地分支
