# Unity 技术文档同步

## 1. 开始前核对

1. 优先读取项目 `.agent-rules/overrides.md` 与 `.agent-rules/project-docs/unity/其他规则/04-UnityAI技术文档任务入口.md`（若已安装），按入口继续核对技术文档组织、编写规范与模板。
2. 先检查仓库既有技术文档目录（如 `项目文档/技术文档/` 或 `docs/`），**沿用现有文件结构与命名**，不因通用模板擅自搬迁已有文档。
3. 以真实源码与配置文件为唯一事实依据：核对 `ProjectSettings/ProjectVersion.txt`、`Packages/manifest.json`、场景入口、核心 `.asmdef`、关键脚本与实际构建脚本。

## 2. 增量同步步骤

1. **评估文档影响面**：根据本次代码/配置改动（如 `git diff` 或变更模块列表），定位受影响的文档章节（技术总览、系统架构图、启动/加载/联调时序图、依赖说明、构建与排障指南），避免无关文档大面积重写。
2. **核对架构与时序图准确性**：
   - 系统架构图清晰体现 Unity 客户端模块分层（展示层 UI / 交互输入 / 业务域 / 资源与网络基础设施 / 平台 SDK 适配）及外部服务边界；
   - 跨端或复杂异步链路（启动引导、资源热更/Addressables 加载、登录与长连接重连）配简洁准确的 Mermaid `sequenceDiagram`。
3. **如实标注验证状态**：明确区分“已从源码核实”“已在目标环境/真机实测验证”与“规划中/待真机确认”，杜绝把历史旧实现或规划接口写成当前现状。
4. **同步检查文件链接**：确保文档内所有相对路径链接与关键类/脚本路径真实存在、无死链。

## 3. 输出结构

- **一、文档影响范围摘要**（受影响文档清单及变更原因）
- **二、同步后的文档更新内容**（直接编辑目标文档或输出清晰变更块）
- **三、源码依据与未验证项清单**（列出本次核对过的核心文件与仍需人工/真机补验的项）

## 4. 交付自检与红线

- 严禁编造不存在的类名、脚本路径、Unity 版本号或未执行的真机性能数据。
- 设计文档（UI/产品）与 Unity 技术实现文档分别维护，不混写覆盖。
