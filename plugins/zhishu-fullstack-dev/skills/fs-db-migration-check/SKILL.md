# 数据库与迁移变更检查

## 1. 开始前核对

1. 优先读取项目 `.agent-rules/overrides.md`、`.agent-rules/common/02-软件版本迭代与发布管理规范.md`（§ 5 数据向后兼容治理）及对应语言包的数据访问规则（`go/05`、`java/07`、`python/07`、`javascript/05`，若已安装）。
2. 核对目标项目实际数据库引擎与版本（MySQL / PostgreSQL / SQLite / MongoDB 等）、既有迁移工具（Flyway / Goose / Prisma / Alembic / 自定义 `schemaVersion` 迁移器）以及表数据量级与停机窗口约束。

## 2. 六维迁移安全核查

1. **零停机与先扩后缩（Expand-Contract）**：
   - 检查是否直接执行 `DROP COLUMN` / `RENAME COLUMN` / 破坏性 `ALTER TYPE`：若线上旧版本服务实例在滚动发布期间仍会读写旧字段，必须拆分为“先新增兼容字段双写 → 切读 → 确认无需回滚后再清理旧字段”两阶段发布。
2. **大表锁表与线上性能风险**：
   - 审查 `ADD COLUMN NOT NULL`（无默认值或触发整表重写）、同步创建大表索引（检查引擎是否支持 `CONCURRENTLY` / `ALGORITHM=INPLACE`）、无分批的大范围 `UPDATE` / `DELETE`（避免长事务锁表与主从延迟飙升）。
3. **数据完整性与幂等可重复执行**：
   - 检查外键/唯一约束新增前是否清理或校验存量脏数据；
   - 核对迁移脚本编号递增、禁止修改已上生产的历史迁移文件；本地文件/配置升级是否带 `schemaVersion`、自动迁移前是否生成安全备份且对更高未知版本拒绝覆写。
4. **索引与查询匹配**：
   - 检查新增高频查询、排序与关联条件是否命中合适联合索引（遵循最左前缀原则），同时避免无节制堆砌冗余索引拖慢写入。
5. **SQL 安全与参数绑定**：
   - 确认迁移与配套 DAO 代码严格使用参数化查询（标识名如需动态拼接必须经严格白名单校验），杜绝 SQL 注入。
6. **明确回滚方案**：核对是否具备可验证的 `down` 迁移或数据备份恢复步骤；对不可逆清洗操作标明备份与审批前提。

## 3. 输出结构

- **一、迁移风险评级**（低风险平滑变更 / 需分阶段发布 / 阻断级破坏性变更）
- **二、逐项检查表**：`严重度 | 脚本或文件位置 | 风险说明 | 安全改造方案`
- **三、推荐上线与回滚执行步骤**（备份 → 预演 → 迁移 → 校验 → 回滚路径）

## 4. 交付自检与红线

- 严禁脱离具体数据库引擎版本武断断言某条 `ALTER TABLE` 一定不锁表；引擎版本未知时必须标注“需在同版本预发库实测锁行为”。
- 任何会删除存量数据或覆写用户配置文件的变更，必须显式标红并要求先备份与明确授权。
