# 代码审查与风险排查

## 1. 开始前核对

1. 优先读取目标项目的 `.agent-rules/overrides.md` 与当前技术栈已安装的入口规则（`javascript`、`typescript`、`go`、`java`、`python` 等），仅套用本项目实际生效的语言规范。
2. 核对项目既有依赖、构建脚本、测试框架与代码风格约定，**严禁以通用规范为由要求替换仓库既有框架或做与当前变更无关的大面积重构**。
3. 完整阅读本次变更的 Diff 与调用上下文（不只看新增行，要看被修改函数的全部调用方与既有测试）。

## 2. 六维审查重点

1. **逻辑正确性与边界条件**：空值/零值/空集合、越界、编码与时区、浮点数精度、状态机非法迁移及错误分支遗漏。
2. **安全红线**：注入风险（SQL / 命令拼接 `shell: true` / XSS / 路径穿越与软链接逃逸）、鉴权与越权校验缺失、硬编码密钥或日志泄露凭据、SSRF 与未限流大文件/压缩包解析。
3. **异步、并发与资源管理**：未捕获 Promise 拒绝、竞态条件与死锁、连接/文件句柄/定时器未释放、上下文取消（`AbortSignal` / `context.Context`）未透传。
4. **兼容性与契约影响**：对外 API、配置文件格式、CLI 参数或共享类型是否发生静默破坏性变更。
5. **可维护性与依赖克制**：是否引入未授权或高风险第三方依赖、是否存在明显重复逻辑或过度抽象。
6. **测试与提交卫生**：核心新增分支与修复缺陷是否有对应回归测试；提交/分支是否符合 `.agent-rules/common/01-Git版本控制规范.md`。

## 3. 输出结构

- **一、审查结论**：可合入 / 需修复阻断项后合入 / 建议退回重做。
- **二、分级问题清单**：`严重度（P0 阻断 / P1 应改 / P2 建议） | 文件:行号 | 问题类型 | 触发场景与后果 | 精准修改方案`
- **三、已运行的检查与未验证范围说明**

## 4. 交付自检与红线

- 每条问题必须锚定真实文件路径与代码行，严禁给出“建议提高代码质量”之类空泛评价。
- 严格区分必改缺陷与个人风格偏好；尊重仓库既有工具链与测试体系。
