# 08 - TypeScript 常见反模式与 AI 自检

> - 🟢 本文件适用于 TypeScript 常见反模式清单与 AI 自检要点。
> - 🔴 不适用：业务逻辑实现

---

## 1. 🔴 高风险反模式与适用边界

### 1.1 any 滥用

```ts
// ❌
function f(x: any) { return x.foo; }
const data: any = JSON.parse(input);
const handler: any = (e: Event) => {};

// ✅ unknown + 完整收窄（TS 4.9+ 无需 as 断言）；项目已有运行时校验方案时复用
function f(x: unknown): string {
  if (typeof x === 'object' && x !== null && 'foo' in x && typeof x.foo === 'string') {
    return x.foo;
  }
  throw new Error('Invalid input');
}
```

**ESLint**：如果项目已采用 typescript-eslint，可在现有配置中评估 `@typescript-eslint/no-explicit-any`；不要把某个等级写成所有项目的强制门禁。

### 1.2 `as` 逃避类型检查

```ts
// ❌ 双断言
const value = unknownValue as unknown as User;

// ❌ JSON.parse + as 跳过校验
const user = JSON.parse(input) as User;

// ✅ 使用项目已有的 schema 或自定义守卫校验；不要因本示例新增依赖
const user = UserSchema.parse(JSON.parse(input));
```

**ESLint**：`no-unsafe-*` 是否启用、启用哪些规则及严重级别，遵循项目现有配置和可接受的误报成本。

### 1.3 `!` 非空断言

```ts
// ❌
const user = users.find(u => u.id === id)!;          // 不存在就崩

// ✅
const user = users.find(u => u.id === id);
if (!user) throw new Error('Not found');
```

**ESLint**：`no-non-null-assertion` 是否启用由项目配置决定；即使未启用，也应审查断言是否有可靠的不变量。

### 1.4 装饰器配置与迁移

```ts
// ⚠️ legacy 装饰器：仅在项目编译链和框架要求时使用
@Component({ selector: 'app' })
class AppComponent {}

// ✅ 标准装饰器：仅在项目已采用对应 TypeScript/框架配置时使用
class Calculator {
  @logged
  add(a: number, b: number) { return a + b; }
}
```

- 先检查 TypeScript 版本、`experimentalDecorators`、装饰器元数据选项、框架编译链和现有签名；标准装饰器与 legacy decorators 的类型和运行时语义不同，不能机械迁移。
- Angular、NestJS、TypeORM 等项目如果依赖 legacy decorators，应沿用锁定版本与配置；迁移需要单独授权、兼容性评估和回归测试。
- `experimentalDecorators` 不应在通用规则中强制开启或关闭；以项目实际配置和框架要求为准。

### 1.5 函数反模式

```ts
// ❌ 默认导出整个对象
export default { getUser, createUser, deleteUser };

// ❌ 职责混杂：把路由控制、业务编排、校验逻辑全部堆进同一文件，难以独立测试与演进
// user.ts 里混杂：UserController + UserService + UserValidator

// ❌ 位置参数过多且含义不直观时仍平铺传参（函数行数与参数数量仅作审查信号，不设固定硬门禁）
function process(
  user: User,
  action: string,
  params: Record<string, unknown>,
  retry: boolean,
  notify: boolean,
) { /* ... */ }

// ✅ 具名导出 + 按职责拆分 + 多选参使用具名 options 对象
export function getUser(id: number): Promise<User | null> { /* ... */ }
export function createUser(input: UserInput): Promise<User> { /* ... */ }

function processOrder(options: { user: User; action: string; retry?: boolean }) { /* ... */ }
```

### 1.6 模块反模式

```ts
// ❌ 内部子目录层层 barrel 重导出（易引发循环依赖、拖慢类型检查与 tree-shaking）
// src/features/index.ts
export * from './user';
export * from './order';
export * from './product';

// ❌ 循环依赖
// a.ts -> b.ts -> a.ts

// ❌ 未经边界控制的全局副作用挂载
globalThis.myApp = { init() {} };

// ✅ 模块内部直接从具体源文件导入 + 保持单向依赖
import { getUser } from './user/user.api';
```

注：库或 monorepo 子包的公开对外入口（如 `packages/<pkg>/src/index.ts`）用于显式暴露公共 API 契约，不属于内部 barrel 滥用；但包内模块互相引用仍应直接指向具体源文件。

### 1.7 类型反模式

```ts
// ❌ 占位 type
type T = any;                                       // 假装有类型

// ❌ 业务代码用条件类型 / 映射类型
type GetFieldType<T, K extends keyof T> = T[K] extends infer R ? R : never;

// ❌ 误把联合类型写成 interface（语法错误）或在同一模块无依据地混用风格
interface Status = 'pending' | 'done';               // ❌ 语法错误（interface 不能表示联合类型）

// ✅ 遵循项目既有约定；未约定时通常用 interface 描述可扩展对象/类形状，type 描述联合/交叉/工具类型
interface User { id: number; name: string; }
type Status = 'pending' | 'done';
```

### 1.8 import 反模式

```ts
// ❌ 混用类型与值导入（单文件转译器或类型剥离模式下难以静态区分；注：tsc 默认会擦除纯类型导入，但仍推荐显式标注）
import { User, getUser } from './user';

// ❌ 省略 node: 前缀并整包通配导入整个内置模块
import * as fs from 'fs';

// ❌ require 混入 ESM
const express = require('express');

// ✅ 显式 import type + 按需具名导入带 node: 前缀的内置模块
import type { User } from './user';
import { getUser } from './user';
import { readFile } from 'node:fs/promises';
```

## 2. 🟡 团队约定补充

### 2.1 命名补充

```ts
// ✅ type / interface PascalCase
interface User { id: number }
type Status = 'pending' | 'done';

// ✅ 泛型参数：单参数常用 T，多参数或语义复杂时使用清晰描述名
type Nullable<T> = T | null;
type AsyncResult<TData, TError = Error> =
  | { ok: true; data: TData }
  | { ok: false; error: TError };

// ❌ 命名带 I 前缀（C# 风格）
interface IUser {}                                  // 不要
```

### 2.2 注释补充

- 🔴 中文主导仓库中，新增或修改的说明性注释、JSDoc 正文应使用中文；若目标仓库本身采用英文或其他语言作为既定注释语言，则遵循仓库既有约定。JSDoc 标签、代码标识符与稳定事件键保持规范原样。
- 🟢 可保留英文的情形仅限：工具可识别标记或指令（如 `TODO`、`FIXME`、`@ts-expect-error`、`eslint-disable`）、协议/标准/第三方专有名词、已明确对外发布的英文 API 契约，以及外部依赖或自动生成代码；在中文主导仓库中，除标记和专有名词外仍应以中文说明含义或原因。
- ❌ 在中文主导仓库中，不得仅因类型名、函数名、变量名或 API 为英文，就把说明性注释整体改写为英文。
- 🔴 方法内部和局部逻辑说明使用 `//`；对外公开或由项目约定要求文档化的 API 使用紧挨声明的 `/** ... */` JSDoc。
- ❌ **禁止**把普通 `/* ... */` 用作业务说明、算法说明或临时禁用代码；连续说明使用贴近代码的多行 `//` 中文注释。
- 🟢 文件级工具指令、不可改动的第三方/生成代码或授权声明需要 `/* ... */` 时，可保留其原有形式。

```ts
/**
 * 计算折扣
 * @deprecated 用 getDiscountV2 替代
 * @see getDiscountV2
 */
function getDiscount(user: User) {
  // 示例省略。
}

/**
 * @throws {ValidationError} 当输入不合法
 * @example
 * const u = createUser({ name: 'alice' });
 */
export function createUser(input: UserInput): User {
  // 示例省略。
  throw new Error('示例未实现');
}
```

### 2.3 公共 API 模式

```ts
// ✅ 显式参数 + 返回类型 + JSDoc + 具名导出 + 状态码/运行时校验 + 取消信号
/**
 * 获取用户
 * @param id 用户 ID
 * @param signal 可选取消信号
 * @returns 用户对象（404 不存在时返回 null）
 */
export async function getUser(
  id: number,
  signal?: AbortSignal,
): Promise<User | null> {
  const res = await fetch(`/api/users/${id}`, { signal });
  if (res.status === 404) return null;
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  const data: unknown = await res.json();
  if (!isUser(data)) throw new Error('Invalid user response');
  return data;
}
```

### 2.4 内部 / 外部 API 分层

```ts
// ❌ 把仅单文件使用的辅助函数随意 export，或把内部模块直接重导出到包公开入口
export function formatInternalKey(id: number) { /* 仅本文件使用 */ }

// ✅ 明确分层：
// 1. 仅单文件使用的辅助函数不加 export
// 2. 包内多文件共享的内部模块（如 src/internal/user-helper.ts）可具名 export，但不从包公开入口（src/index.ts / package.json exports）对外暴露
// 3. 对外契约集中在公开入口（如 src/api/user.ts / src/index.ts）显式导出
```

## 3. 🟢 可选 · 自检工具

以下工具只用于说明能力类别。项目已经采用或用户明确授权时才可执行对应命令、更新 lockfile 或新增 CI 门禁；否则使用现有工具完成等价检查。

### 3.1 ts-unused-exports

检测未使用的 export（存量项目已配置时可继续沿用；新选型通常优先评估下方 §3.4 的 `knip`，可一并检测未使用的 export、文件与依赖）。

### 3.2 dependency-cruiser

依赖图 / 循环依赖检测。

```js
// .dependency-cruiser.cjs
module.exports = {
  forbidden: [
    {
      name: 'no-circular',
      severity: 'error',
      comment: '禁止循环依赖',
      from: {},
      to: { circular: true },
    },
  ],
};
```

```bash
npx depcruise src
```

### 3.3 type-coverage

类型覆盖率门槛必须沿用项目现有配置；不得从本节写入固定百分比。覆盖率只能帮助发现未标注区域，不能证明类型设计正确。

### 3.4 knip（未使用代码检测）

检测未使用的 export / 文件 / 依赖。
