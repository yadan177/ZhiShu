# 15 - 产品设计 AI 通用入口规则

> - 🟢 本文件适用于 AI 参与的需求调研、产品结构图梳理、PRD 编写、需求自检、会议纪要转待办与验收清单生成。
> - 🔴 不适用：编造市场数据或用户访谈结论、擅自替业务方拍板关键范围取舍，或把规划目标写成已上线功能。

---

## 1. 开始前核对

执行产品设计任务前，先读取[总览](./00-文档总览.md)及当前项目已有文档与代码现状：

1. **核对现状基线**：先读取仓库或项目已有文档、代码入口与版本状态，不凭记忆假设功能已经存在。
2. **明确任务性质**：区分本次是探索调研、结构梳理、新写 PRD、增量改稿、需求自检还是生成验收清单。
3. **锁定目标平台与角色**：明确目标用户群体、运行平台（Web / 桌面 / 移动 / XR 头显）及已确认的边界约束。

- 🔴 调研结论与外部竞品机制必须标注信息来源、核验日期与证据级别；无法核实的数据必须标明“待核实”，严禁编造数字。
- 🔴 遇到模糊或冲突需求时，先基于已有事实完成可独立推进的分析与草案，再将真正需要拍板的未决问题集中列出（附可选方案与利弊），避免每步琐碎反问。
- 🟡 若项目已安装 `xr-common` 规则包且当前需求涉及 XR，应结合 `xr-common` 的硬件档位与舒适度红线进行需求自检。

## 3. 决策与边界约束

- 🔴 产品文档聚焦“**解决什么问题、面向谁、边界是什么、行为与验收是什么**”，不越权规定研发内部数据库表结构或 UI 具体像素细节（除非项目有明确契约要求）。
- 🔴 严禁为了文档看起来完整而塞入未经业务确认的 P2/远期功能并混作 P0 本期交付。
- 🔴 会议纪要转待办时，必须区分 **已达成决策**、**明确行动项（含负责人/产物/时间，缺失则标待定）** 与 **仍待讨论议题**，不得把口头随口一提的想法写成已批准需求。
- 🔴 修改既有 PRD 时说明变更点、变更原因及受影响的下游页面、接口或验收用例，不静默删除已有约束。

❌ 反例：根据一句“帮我写个 XR 协作 PRD”，擅自编造“支持 50 人同屏实时语音与云端渲染”，且未标注属于假设。

✅ 正例：先界定本期最小闭环假设（如目标一体机档位、并发人数上限、离线降级策略），把未确认项集中在“待决策问题清单”中供产品负责人确认。

## 4. 交付与报告

完成产品文档或审查输出后，简要说明：

1. 本次所依据的现状基线、参考文档或会议输入。
2. 核心产出内容（结构图 / PRD / 盲区清单 / 验收清单）及范围边界。
3. 本次识别出的关键风险、跨岗位依赖与待拍板问题。
4. 尚未核实的信息来源或需补充的真实调研项。
