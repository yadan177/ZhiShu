# 01 - 需求范围与产品结构规则

> - 🟢 本文件适用于需求调研、产品定位、范围边界界定、信息架构（IA）与产品结构图梳理。
> - 🔴 不适用：未经验证将竞品宣传文案当作技术可行依据，或以堆砌功能清单替代用户任务分析。

---

## 1. 调研与事实口径

- 🔴 调研文档必须区分**一手事实**（官方最新文档、实机测试、本仓库源码）、**二手公开资料**（文章/案例）与**主观推论**。
- 🔴 竞品对比聚焦用户任务路径、信息架构、边界取舍与实现门槛，不做“人家有所以我也要做”的机械照抄。
- 🔴 引用外部能力或平台特性时注明平台、版本与核验日期；涉及硬件/SDK 能力时，严禁把概念演示片当成可量产能力。

## 2. 产品定位与范围边界（Scope & Non-Goals）

任何产品方案或大版本立项必须写清四项基本契约：

1. **目标用户与角色**：谁来用、高频使用频率、专业背景与操作环境。
2. **核心问题与价值**：当前真实痛点是什么，本方案具体改变了什么。
3. **本期交付范围（In Scope）**：按优先级（P0 必做 / P1 重要 / P2 后续）清晰拆分，并说明核心闭环。
4. **明确不做（Non-Goals）**：主动划出边界，防止在设计、开发与评审阶段反复蔓延。

❌ 反例：只写“打造一站式全能平台，支持所有主流工具和全部岗位”，无优先级和明确不做项。

✅ 正例：明确本期首期覆盖的岗位、目标工具清单与核心闭环，将暂不预设的扩展方向单独归入“后续演进占位”。

## 3. 信息架构与产品结构图规范

产品结构图（XMind / 脑图）是呈现**用户可见界面层级、页面元素、列表字段与交互去向**的“结构 X 光片”，与 PRD（业务规则/状态机/验收）和技术架构图（系统模块/接口/CLI）职责分离，不得混写为一团。

### 3.1 信息架构边界

- 🔴 **纯用户可见视角**：根节点下直接挂接用户实际看到的一级入口（导航/Tab），严禁在顶层混入工程壳层词（如「全局组件」「窗口保护」）、设计稿编号（如 `01 ·`）、UI 像素尺寸（如 `216px`）、代码环境变量或后端实现原理。
- 🔴 **命名通俗且全域一致**：结构图、PRD、UI 设计稿中的一级入口、页面名、Tab 名、实体名必须完全一致，避免同一概念出现多个别名。
- 🔴 **并行概念不混叠**：属于不同作用域或生命周期的对象（如项目级配置 vs 用户级资产、复合插件 vs 独立技能 vs 外部连接器）在结构上必须并行拆分，不重复挂载。
- 🔴 **空态与入口显式挂接**：当前暂未预设内容的列表或模块，必须标出空态提示与用户导入/创建入口，不填虚假占位数据。

### 3.2 节点颗粒度与标准拆法

- 🔴 **极简短语命名**：每个节点优先使用 **2–7 字短名词或动宾短语**（如 `搜索框`、`项目名称`、`进入项目规则页`），严禁在节点里塞入括号长解释、完整句子、交互细则或技术参数（这些内容归 PRD 或设计标注）。
- 🔴 **「列表 + 列表信息」成对拆解**：凡涉及数据列表（如聊天列表、项目列表、资产列表），必须成对拆为两个兄弟节点——**`xxx列表`**（挂接点击列表项后进入的子页面/详情类型）与 **`列表信息`**（逐项列出该行/卡片上用户可见的原子字段，如头像、名称、状态徽章、时间、操作按钮），确保 UI 与研发不漏字段。
- 🔴 **概要归口 `]` 表达交互去向**：在 XMind 等支持概要（Summary）的工具中，用原生概要 `]` 将列表入口与列表信息或同组触发项归口指向目标页面/弹窗（例如 `选择一个群` 下的「群列表 + 列表信息」以 `]` 归口到 `进入群聊`）。
- 🟡 页面内节点按用户视觉浏览顺序（从上到下、从左到右）排列，单一产品主界面优先收敛为单张高密度画布；确需展示数据资产结构或系统架构时，另建独立架构图，不污染产品结构图。

❌ 反例：把产品结构图画成缩略版 PRD + 架构图——根节点下设「应用导航与窗口」「全局弹窗与通用组件」，节点写 `左侧导航栏（216px）`、`单实例运行（防多开同时写入冲突）`、`开发调试隔离目录（ZHISHU_DEV_PROFILE）`，并在同一份结构图里堆砌 CLI 返回码和底层原子写入机制。

✅ 正例：根节点下只挂一级主模块，列表页严格拆成短词节点与成对字段：

```text
我的项目
├── 搜索框
├── 添加项目
├── 项目列表
│   └── 进入项目规则页
└── 列表信息
    ├── 项目名称
    ├── 项目路径
    ├── 来源标签
    ├── 适用 AI 工具
    ├── 规则包摘要
    ├── 状态徽章
    ├── 管理规则按钮
    └── 移出列表按钮
```

## 4. 变更与范围控制

- 🔴 中途新增或调整需求时，必须评估对已有信息架构、数据口径、上下游岗位（UI / 美术 / 研发）及排期的影响。
- 🔴 删除某项页面模块或能力时，同步检查结构图、PRD、UI 设计稿与关联文档，确保无残留死入口或矛盾描述。
